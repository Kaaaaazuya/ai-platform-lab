# ADR-008 評価の仕組み

ステータス: Proposed（案Aで実装済み。決定者の確認待ち）

## 要約

- 評価データセットとスコアはLangfuseに置き、評価の実行と回帰の判定は自作のランナーで行う。Langfuseへの記録は任意で、鍵（`.env` の値）がなければレポートだけを作る
- ケースごとに、検索の的中、引用の有無、正しさ、根拠への忠実さ、レイテンシを記録する
- 評価はローカルで実行してレポートをコミットし、CIはベースラインとの差分を見る

## 背景

LLMアプリの改善では、直したつもりで別の質問の答えを悪くすることがよくある。プロンプトを1行変えるだけで、回答の傾向は大きく変わりうる。そこで、変更の前後で同じ質問の集まり（評価データセット）を流し、点数で比べる必要がある。これがデザインドックの「改善のアウターループ」の要だ。

RAGの評価では、少なくとも次の2つを分けて見る。

- 検索：答えが書かれたドキュメントを取ってこられたか
- 生成：取ってきた内容に基づいて、正しく答えられたか

生成の良し悪しは機械的に判定しにくい。そこで、別のLLMに採点させる方法（LLM-as-a-judge）がよく使われる。採点役のLLMは揺れるので、少しの差は許すしきい値が要る。詳しくは[評価ランナーの解説](../components/evaluation.md)を参照。

## 検討した選択肢

### 案A：Langfuse のデータセットと LLM-as-a-judge

- 長所：観測と評価が1か所にまとまる。トレースにスコアを付けるので、低評価の回答の中身（プロンプト、検索結果）をすぐ見られる
- 短所：CIとの連携や回帰の判定は自分で組む
- 学べること：評価の指標の設計、LLM-as-a-judgeのプロンプト、改善ループの全体

### 案B：promptfoo

- 長所：設定ファイルで評価を書け、CIで回しやすい。比較の画面もある
- 短所：結果がLangfuseと分かれる。トレースとスコアを行き来しにくい
- 学べること：評価の宣言的な書き方

### 案C：Ragas

- 長所：RAG向けの指標（忠実さ、回答の関連性、文脈の適合率など）が揃っている
- 短所：単独では運用の仕組みがない。指標の中身を理解しないまま数字を見ることになりやすい
- 学べること：RAG評価の標準的な指標

## 比較

| 観点 | 案A：Langfuse＋自作ランナー | 案B：promptfoo | 案C：Ragas |
| --- | --- | --- | --- |
| トレースとの結び付き | 強い | 弱い | 弱い |
| CIでの回しやすさ | 自作 | 高い | 自作 |
| RAG向けの指標 | 自作（必要なものだけ） | 一部 | 豊富 |
| 仕組みの見えやすさ | 高い | 中程度 | 中程度 |

## 判断材料・確認すること

- [x] 判定役のモデル：Ollamaで十分か、Bedrockが必要か → まずOllama（チャットと同じモデル）。採点がぶれるならM5でBedrockと比べる
- [x] 評価データセットの初期件数と作り方（ADR-009と連動） → OpenTelemetryのconceptsから15件を手で作った
- [ ] OTelトレースのどのspanにどの評価をかけるか（検索spanに関連性、生成spanに根拠の有無など）と、サンプリング率
- [x] CIの合格条件に入れるレイテンシ・コストのしきい値 → レイテンシは中央値が1.5倍を超えたら悪化。コストはトークン数が取れてから足す

## 決定（案）

案Aで実装した。評価データセットとスコアはLangfuseに置き、評価の実行と回帰の判定は自作のランナーで行う。

**評価の流れ**

1. `eval/rag-cases.jsonl` の質問をRAGチャットに流す。チャット本体と同じ処理を通るので、ガードレールと検索の処理がトレースに残る
2. ケースごとに次を記録する
    - 検索の的中：期待する資料が検索結果に入ったか
    - 引用の有無：回答に `[1]` のような引用があるか
    - 正しさと根拠への忠実さ：判定役のLLMが1〜5で採点する（LLM-as-a-judge）。判定役もゲートウェイ経由で呼ぶ
    - レイテンシ：全体と最初のトークンまで
3. スコアをLangfuseのトレースに付け、データセットの実験（run）として記録する。Langfuseの画面で実験どうしを比べられる
4. 集計を `eval/reports/latest.json` に書く

**回帰の判定**

- `eval/baseline.json` と比べ、しきい値を超えて下がった指標があれば失敗にする
- しきい値：検索の的中率と引用の付与率は10ポイント、正しさと忠実さは0.3、レイテンシは中央値が1.5倍
- 評価にはLLMが必要なので、CIでは動かさない。手元で `task eval` を実行し、レポートをコミットする。CIはベースラインとの差分をジョブのサマリーに出し、悪化があれば失敗させる
- 良くなったら `task eval-baseline` でベースラインを更新する

**決定（案）の理由**

- 改善ループの起点はLangfuseのトレースなので、スコアを同じ場所に置くと調査が速い
- 指標を自分で作ることで、何を測っているかを理解できる。学習の目的に合う
- Ragasの指標は、必要になったら一部を取り込める

**影響**

- ADR-003：ベクトルストアを変えたとき、検索の的中率で比べられる
- ADR-005：ガードレールのケースも評価データセットとしてCIで判定している
- ADR-009：評価データセットは題材（OpenTelemetryのドキュメント）から作った

**受け入れること**

- CIはコミットされたレポートを信じるだけで、評価そのものは再実行しない。レポートを更新し忘れると差分が出ない
- 判定役がチャットと同じローカルモデルなので、自分の回答に甘くなりうる。採点の揺れも大きい
- 本番トラフィックへのspanごとの自動評価（Langfuseの評価機能）は、まだ設定していない
