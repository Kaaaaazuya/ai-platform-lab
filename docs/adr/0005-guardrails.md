# ADR-005 ガードレールの実装位置とログ方針

ステータス: Accepted（2026-11-16）

## 要約

- PIIの検出は、Presidio と日本向けの独自ルールの2段で行う。プロンプトインジェクションはルールで検知する
- ガードレールはアプリAPIから呼ぶ。インジェクションの疑いがあればLLMを呼ばずに止める
- トレースと会話履歴には、マスクした後の本文だけを残す

## 背景

社内AI基盤では、利用者が個人情報や機密を入力してしまうことを前提に設計する。金融系の業務なら、口座番号や氏名が問い合わせに混ざるのは珍しくない。何も対策しないと、次の場所に生のPIIが残る。

- LLMへの入力（外部のモデルなら社外に出る）
- 観測基盤のトレースとログ
- 会話履歴のデータベース

もう1つの脅威がプロンプトインジェクションだ。「これまでの指示を無視して」のような入力で、システムプロンプトを書き換えたり、内部の情報を引き出したりする攻撃を指す。

ガードレールをどこに置くかで、効く範囲と遅延が変わる。Uberはゲートウェイに PIIマスクを組み込んでいるが、入力が長いほどレイテンシが増えると報告している。あわせて、改善ループ（ADR-008）では本文を読み返したい。「残したいが、生のPIIは残したくない」という両立も決める必要がある。仕組みの詳細は[ガードレールの解説](../components/guardrail.md)を参照。

## 検討した選択肢

### 案A：ゲートウェイの連携でPresidioなどを呼ぶ

- 長所：全LLM呼び出しが必ず通る。アプリが増えても漏れがない
- 短所：レイテンシが増える。Envoy AI Gatewayのスタンドアロンモード（`aigw run`）で外部処理を挟めるかが未確認
- 学べること：Envoyの外部処理（ext_proc）、ゲートウェイでの一元的な統制

### 案B：LLM Guardなどを別コンテナ（サイドカー）として置く

- 長所：検出器を差し替えやすい。プロンプトインジェクションの検出モデルも使える
- 短所：通信が1ホップ増える。検出モデルの分だけメモリを使う
- 学べること：検出器の比較、機械学習ベースの検知

### 案C：実AWSでは Bedrock Guardrails を使う

- 長所：マネージドで、PII、話題の制限、有害表現などをまとめて扱える
- 短所：ローカルで再現できない。使うたびに課金される
- 学べること：AWSのマネージドなガードレール。M5で比べる対象になる

### ログ方針の候補

| 方針 | 改善ループでの使いやすさ | PIIの残りにくさ |
| --- | --- | --- |
| 本文をそのまま残す | 高い | 低い（生のPIIが残る） |
| マスク後の本文を残す | 中程度（PIIの箇所は種別名になる） | 高い |
| メタデータだけを残す | 低い（中身を読み返せない） | 最も高い |

## 判断材料・確認すること

- [x] 日本語のPII（氏名、住所、口座番号など）をどこまで検出できるか試す → 独自ルールで対応（決定を参照）
- [x] 改善ループには本文が必要なので、マスクとの両立方法を決める → マスク後の本文を残す
- [x] ストリーミングで表示した後に出力検査で引っかかった場合の扱い（表示済みの回答を差し替えるか、チャンクごとに検査するか）。ADR-011より → 生成完了後に差し替える

## 決定

案Aを変形して採用する。ガードレールは**アプリAPIから呼ぶ**（ゲートウェイの外部処理にはしない）。ログは**マスク後のみ**記録する。

**構成**

- PII検出は2段にする
    - Presidio（`presidio-analyzer`コンテナ）：メール・カード番号・IPアドレスなどの汎用ルール
    - アプリ側（`app/api/src/guard.ts`）：日本向けのルール（電話番号、口座番号、マイナンバー、郵便番号、ラベル付きの氏名）
- プロンプトインジェクションはルールベース（日本語・英語の典型パターン）で検知し、該当したら**LLMを呼ばずに**ブロックする
- 入力は検査後にマスクし、以降の埋め込み・生成・トレース・会話履歴にはマスク後の文字列だけを渡す
- 出力は生成の完了後に全文を検査する。PIIがあれば `guard`（`redact`）イベントでマスク後の全文を送り、画面の回答を差し替える。履歴とトレースにはマスク後の回答だけを残す
- ゲートウェイ（aigw）は `OPENINFERENCE_HIDE_OUTPUTS=true` にして、生の生成結果をspanに残さない
- 判定結果はspan属性（`guard.blocked`、`guard.pii.entities`、`guard.injection.rules`）に載せる。検出があれば `langfuse.observation.level=WARNING` にし、改善ループではこれを手がかりにLangfuseから抽出する
- Presidioに届かないときは独自ルールだけで続ける（fail-open）。理由は `guard.presidio_error` に残す
- 攻撃・PIIのケースは `eval/guard-cases.jsonl` に置き、CIのテストで毎回判定する

**ゲートウェイの外部処理にしなかった理由**

- `aigw run`（standalone）で外部処理を挟めるかが未確認で、M3を止めたくない
- 日本向けのルールを書く場所としてはアプリのほうが速く回せる
- 代わりに「アプリを経由しないLLM呼び出しには効かない」。評価ランナーなど他の呼び出し元が増えたら、ゲートウェイ側へ移すかを見直す

**影響**

- ADR-002：ゲートウェイには検査を入れていない。生成結果の本文をspanに残さないよう、ゲートウェイを設定した
- ADR-004：Langfuse と Grafana に届く本文はマスク後になる
- ADR-008：評価データセットにガードレールのケース（`eval/guard-cases.jsonl`）を置き、CIで毎回判定する
- ADR-011：生成中のトークンは画面に出るので、出力の検査は表示の後になる

**受け入れること**

- 表示中の回答に一瞬PIIが見える（差し替えは生成完了後）。チャンクごとの検査は遅延が増えるのでやらない
- 日本語の氏名はラベル（「氏名：」など）付きのものしか拾えない。NERは未導入
- ルールベースの検知は言い換えに弱い。見逃しはLangfuseのトレースから拾ってケースに足す（ADR-008）
